# Финальная инженерная проверка

Область завершающего прогона сужена пользователем: **браузерные проверки исключены**.
Это не означает PASS браузерного end-to-end: Chromium ранее не запускался, а пробный запуск
установленного Firefox завершился тайм-аутом до открытия приложения и передачи файлов.
Никакие браузеры или пакеты не устанавливались. Node UI-тесты и успешная HTTP-передача
не заменяют проверку загрузки настоящим браузером.

В завершающей проверке повторяются Java/JS regression suites и OSM roads + water в двух режимах.
Конкурсные эталоны, детерминизм, witness routes, HTTP-контракты и recovery уже входят в Java suite.
Измерения 50/100/500 ОКС и Docker/HTTP smoke предыдущего этапа переиспользуются только после проверки
идентичности production bytecode, входных SHA-256, статических ресурсов и конфигурации.
Production-код, frontend, настройки памяти и лимиты графа в этой итерации не изменяются.
Сцена 250 ОКС остаётся контролируемым `COMPLEXITY_LIMIT`; точная причина измерена ниже.

Итоговые измерения и статусы: [verification.json](verification.json). Неуспешный ресурсный
прогон остаётся `COMPLEXITY_LIMIT`; он не обозначается как успешный расчёт или как доказанная
геометрическая недостижимость. Промежуточный 900-секундный probe отдельно сохранён как `TIMEOUT`.

Полный отчёт предыдущего этапа сохранён в
[benchmark-verification.json](benchmark-verification.json). В публикуемых отчётах абсолютный
путь локального checkout заменён на `<repo>`; результаты измерений не изменены.

## Воспроизведение

При наличии подготовленного Docker image `lct-robustness-builder:baseline`, Maven cache
`lct-robustness-m2`, Node, Python с Shapely/pyproj и Chromium/Playwright:

```bash
python3 scripts/verify-finalization.py --phase all --label defence-recheck --control defence-recheck-accounting --generate
```

Сравнение использует сохранённую исходную сборку `target/scale-builds/finalization-profile`.
Для нового эксперимента исходную сборку необходимо сохранить **до** изменения кода через
`scripts/benchmark-scale.py --snapshot --label <before>`, затем передать `--before <before>`.
Без исходного снимка нельзя заново измерить историческое «до» по одному его SHA-256.

Этапы можно запускать отдельно через `--phase tests|bench|stress|ablation|http|browser|stop|report`.
Испытания выполняются последовательно: CPU quota 8, heap 2 ГиБ, memory limit контейнера 4 ГиБ.
Успешные серии 17/50/100 ОКС используют warm-up и четыре warm runs; отрицательные ресурсные
сценарии останавливаются при первом подтверждённом отказе, без бессмысленного повторения.
Полный probe 500 ОКС отделён от повторных измерений построения графа.

HTTP/browser smoke создаёт новый Compose project с собственными томами, исходным Dockerfile
и исходным `caddy/Caddyfile`. После проверки `stop` удаляет только контейнеры этого проекта;
его тестовые volumes сохраняются для осмотра. Production volumes не используются.
Повторный запуск архивирует прежние файлы отчёта только после остановки тестового проекта.
Runner не устанавливает пакеты и не выполняет команды Git.

Runner обнаруживает уже установленный `playwright`/`playwright-core` и доступный Chromium
или Firefox. Выбор можно переопределить переменными `PLAYWRIGHT_MODULE`, `BROWSER_ENGINE`
(`chromium`/`firefox`) и `BROWSER_EXECUTABLE`; runner ничего не устанавливает.
Браузерный тест использует отдельный persistent profile, настоящий
file input, `Blob.slice()` и HTTP через Caddy. Перезапуск браузера не подменяется импортом
localStorage из тестового кода.

## Данные и измерения

- `target/scale-data/original.geojson` — неизменённый конкурсный файл из `ТЗ/`.
- `consumers-50/100/250/500.geojson` — воспроизводимые плотные синтетические сцены с общей сетью,
  водным барьером и дорогой; генератор `scripts/generate-scale-datasets.py --only-consumers`.
- OSM/вода/смешанные ограничения и witness-сцены — прежние manifests в `examples/stress/`.
- `scripts/generate-upload-fixtures.py` создаёт валидный GeoJSON на 100 МиБ, 1 ГиБ и 2,8 ГиБ:
  исходные 144 геометрии и ограниченные текстовые поля. Это тест объёма передачи, а не городской
  геометрической сложности. Успешная загрузка и успешный расчёт имеют отдельные статусы.

Сырые результаты, точные команды, output SHA-256 и логи находятся в `target/scale-results/`
и `target/final-engineering/`. RSS/heap собираются отдельно; RSS не подменяется значением `Xmx`.
HTTP smoke дополнительно снимает NMT и проверяет сохранность входов, состояние PostgreSQL,
автоматический restart app и приём нового задания после сбоя.

## Изменение графа

Перед дорогой JTS-проверкой отрезок проверяется по небольшому индексу внутренних прямоугольников
запрещённых полигонов. Прямоугольник предварительно доказанно содержится в исходном полигоне;
учитываются исключения для конкретного отрезка. Быстрая проверка умеет только доказать запрет.
Во всех остальных случаях выполняется полный прежний геометрический контроль.
Road/tram, линейные коммуникации, отверстия и неподходящие формы не освобождаются от проверок.
Индекс ограничен 4096 сертификатами на пространство отступов и не является глобальным кэшем.

Число рассматриваемых пар, быстрых отказов и полных проверок публикуется раздельно.
Лимит полных проверок остаётся 50 млн; лимиты узлов и рёбер также сохранены.
Отдельная контрольная сборка отключает только быстрый отказ при **том же** новом учёте бюджета.
С ней сравниваются точный SHA-256 графа (координаты, порядок, направленные рёбра, веса, flags),
число JTS-операций и warm runtime. Это отличает реальную экономию работы от переноса счётчика.

Правила трассировки, стоимость, гидравлика, количество кандидатов, стратегии и независимый
валидатор не изменяются. Пространственная кластеризация и параллельные стратегии не включены.
Протокол загрузки, идемпотентность и границы восстановления описаны в
[docs/resumable-upload.md](../../docs/resumable-upload.md).

## Подтверждённые измерения полных расчётов

Медианы четырёх прогонов после отдельного warm-up, на одной машине и с одинаковыми квотами.
Heap/RSS — медианы измеренных пиков отдельных прогонов, в МиБ; CPU — процессорное время JVM,
которое может превышать wall-clock при работе нескольких потоков.

| Сцена | Wall до → после, с | CPU до → после, с | Peak heap до → после, МиБ | Peak RSS до → после, МиБ |
|---|---:|---:|---:|---:|
| Исходный PLANAR, 17 ОКС | 27,00 → 26,00 | 134,63 → 136,37 | 438,05 → 453,37 | 838,24 → 862,29 |
| Исходный DEPTH, 17 ОКС | 28,52 → 28,68 | 137,51 → 141,74 | 428,78 → 448,04 | 834,12 → 888,30 |
| Плотный PLANAR, 50 ОКС | 9,59 → 8,46 | 23,04 → 15,53 | 388,11 → 379,00 | 800,30 → 798,52 |
| Плотный PLANAR, 100 ОКС | 40,01 → 34,52 | 85,22 → 50,73 | 423,10 → 411,23 | 845,17 → 815,03 |

Во всех этих сериях outputs до/после совпадают побайтово. На исходном наборе ускорение
не заявляется: DEPTH практически не изменился, а RSS немного вырос. Измеримая польза —
плотные сцены 50/100 ОКС: wall-clock меньше на 11,7%/13,7%, CPU — на 32,6%/40,5%.
Полные геометрические проверки: 1 728 621 → 868 973 и 5 492 871 → 1 816 922 соответственно.
Время до контролируемого отказа в более сложной сцене не включается в таблицу успешных расчётов.

Полный холодный прогон 500 ОКС завершён: 500/500 в трёх вариантах, `valid=true`, 0 errors/warnings,
независимый инженерный oracle без замечаний. Best score — 107,8621699600001, wall-clock — 2082,10 с,
CPU — 2303,38 с, peak heap — 723,53 МиБ, peak RSS — 1037,97 МиБ. Это один полный прогон,
не медиана повторений. Исходная версия останавливалась при построении подходов к ОКС;
процент ускорения полного расчёта для неё определить нельзя.

После оптимизации полный прогон 500 ОКС выполнил 16 018 693 полные проверки и 26 766 590
JTS intersection-вызовов; 86 180 815 пар отвергнуты доказательством пересечения запрещённой области.
Итоговый граф: 14 532 вершины, 2 427 735 направленных рёбер; 8407 Dijkstra-проходов,
49 143 кандидата, 37 074 пересчёта гидравлики и 52 193 копирования топологии. Fallback не потребовался.
Число рассматриваемых пар — 145 845 283; это отдельная метрика, не число полных JTS-проверок.

Контрольный эксперимент построения графа 500 ОКС (один warm-up + четыре повтора с обеих сторон):
91,81 → 16,19 с wall-clock (−82,4%), 554,02 → 90,46 с CPU. Полных проверок
38 795 043 → 5 626 935 (−85,5%), JTS intersection-вызовов 44 043 408 → 5 977 273 (−86,4%).
Peak heap: 618,76 → 519,51 МиБ; RSS: 962,54 → 957,69 МиБ.
Все десять построений имеют одинаковый SHA-256 графа
`9d42bd13e7f2fa7a6e7339fb66f645799cdf8b30acebaca40b251b0d9e972e8f`.
Контроль использует тот же учёт 50 млн **полных** проверок, отключая только быстрые сертификаты.
Это ускорение построения графа, не всего расчёта 500 ОКС.

Сцена 250 ОКС остаётся контролируемым отрицательным тестом: `separate-connections` достигает
лимита 4 млн направленных рёбер и весь job завершается `COMPLEXITY_LIMIT`. Первые четыре стратегии
подключили 250 ОКС, но это не выпущенный валидированный результат. Плотность и расположение объектов
влияют на сложность: успешные 500 ОКС не означают успех любой сцены с меньшим числом потребителей.

## Завершающее измерение 250 ОКС

Профилирование выполняется на копиях трёх Java-файлов в `target/`, с observer из тестового
каталога. Исходные production-файлы не редактируются. Наблюдатель не меняет рёбра, веса,
порядок обхода, набор кандидатов или ограничения. Структурные счётчики в точке отказа совпали
с предыдущим прогоном: 8983 вершины, 3 999 302 направленных ребра, 8 385 891 полная проверка.

| Этап | Статические вершины | Динамические вершины | Направленные рёбра |
|---|---:|---:|---:|
| Только статический граф | 3975 | 0 | 222 874 |
| Подходы к ОКС и точки присоединения | 3975 | 2087 | 502 518 |
| Конец совместных стратегий | 3975 | 2828–2909 | 669 778–712 051 |
| `separate-connections`, перед отказом | 3975 | 5008 | 3 999 302 |

В последней строке: 1960 подходов к ОКС, 127 точек присоединения, 2921 точка ветвления.
Исходящие рёбра точек ветвления — 2 972 838 (74,33% графа). Следующая вставка требует ещё
2761 ребро и превысила бы сохранённый лимит: 4 002 063 > 4 000 000.
Уникальных неориентированных связей — 2 001 212; повторных направленных связей между одинаковыми
ID — **0**. Две ориентации нельзя механически объединять: переходы через road/tram могут быть
односторонними. В каждом начале стратегии граф возвращается к 502 518 рёбрам — утечки между
стратегиями нет. Adaptive fallback и расширение локального региона не запускались.

3 329 229 рёбер (83,25%) не перечислялись Dijkstra в данной стратегии до отказа. Это наблюдение,
а не доказательство их ненужности в будущем: набор терминалов и динамические препятствия меняются.
590 совпадающих координат также не означают эквивалентность вершин: роли подхода/навигационной
вершины и точки присоединения имеют разные правила транзита, направления и идентификаторы.
Удаление таких вершин или связей без доказательства эквивалентности не внедрялось.

Причина — плотные связи накопленных кандидатов ветвления в стратегии отдельных подключений,
а не повторные ID-рёбра, повреждённые ограничения, fallback или недостаток heap. Ленивое построение
adjacency потребовало бы отдельно доказывать эквивалентность при изменении терминалов; в этой
финальной осторожной итерации такая переработка не выполняется. Корректный `COMPLEXITY_LIMIT`
сохраняется, не выдаётся за геометрическую недостижимость и не считается успешным расчётом.

Команды завершающей проверки:

```bash
python3 scripts/profile-dense-graph.py --label dense-250-audit-fresh
python3 scripts/verify-finalization.py --phase tests --label acceptance-close-fresh
python3 scripts/run-stress-suite.py --skip-build --docker-image lct-robustness-builder:baseline --maven-cache lct-robustness-m2 --manifest examples/stress/universal-manifest.json --scenario competition-osm-roads-water --mode BOTH --repeat 1 --out target/acceptance-close/osm-water-fresh
python3 scripts/summarize-acceptance-close.py --label acceptance-close-fresh --audit dense-250-audit-fresh --osm-out target/acceptance-close/osm-water-fresh
```

Команды создают свежие результаты и передают их summarizer. Без аргументов summarizer собирает
сохранённый прогон `acceptance-close` / `dense-250-audit-run1`. Профилировщик возвращает exit code 2
при подтверждённом `COMPLEXITY_LIMIT`, не скрывая отрицательный результат. Для восстановления
его отчёта после прерывания без повторного расчёта предусмотрен `--summarize-only`.

## Бюджет production-памяти

Production Compose и JVM flags в этой задаче не изменены. Локальные проверки используют
`-Xmx2g` и лимит контейнера 4 ГиБ; реальные RSS и Native Memory Tracking сохранены в JSON.
Это не измерение предельного потребления на сервере с 16 ГБ RAM.

Для планирования размещения на 16-ГиБ хосте разумный консервативный старт — heap не более
10 ГиБ при лимите app 12 ГиБ, оставляя около 4 ГиБ PostgreSQL, Docker и ОС. Это предложение
для отдельной проверки на сервере, **не применённая и не сертифицированная конфигурация**.
`Xmx13g` нельзя сочетать с лимитом контейнера 13 ГиБ: heap не включает native memory JVM.
Текущие лимиты геометрической сложности и self-healing сохраняются; лимит транспорта 3 ГиБ
не гарантирует вычислимость любой сцены такого размера.
