# Эксперименты масштабируемости

Генератор: `scripts/generate-scale-datasets.py`. Измеритель: `scripts/benchmark-scale.py`.
Машинный отчёт: [verification.json](verification.json). Исходные измерения и GeoJSON результатов
сохраняются в `target/scale-results/`; замороженные сборки — в `target/scale-builds/`.
Исходный конкурсный файл и прежние stress fixtures не заменяются.

## Воспроизведение

Из корня проекта, при наличии Docker, Node, Python с Shapely/pyproj и подготовленного Maven cache:

```bash
python3 scripts/verify-scale.py --label rerun --generate
```

Команда генерирует данные, запускает Java/UI, сохраняет сборку, измеряет чтение и полные расчёты,
проверяет SHA-256 конкурсного результата, независимую валидацию и детерминизм сложных сцен.
Большие GeoJSON требуют около 5 ГБ диска. Используется отдельный контейнер на каждый эксперимент;
production-контейнеры и volumes не затрагиваются. Docker smoke описан отдельно в JSON-отчёте.
По умолчанию используется уже подготовленный образ `lct-robustness-builder:baseline` и cache
`lct-robustness-m2`; их можно задать через `--image` и `--cache`. Runner ничего не устанавливает на хост.

Для нового сравнения до/после **до изменения исходников** выполнить `mvn test-compile`, сформировать
`target/stress-classpath.txt` через `dependency:build-classpath` и сохранить сборку:

```bash
python3 scripts/benchmark-scale.py --label before-new --snapshot
python3 scripts/benchmark-scale.py --label before-new --phase parse --counts 1000000 --repeat 4
```

После изменения и компиляции использовать другое имя сборки. Существующие снимки и отчёты не перезаписываются.
`--harness` позволяет использовать новый измеритель с прежними production-классами; это отражается в metadata.
Старые снимки не восстанавливаются командами Git.

## Данные

| Набор | Объекты | Назначение |
|---|---:|---|
| `city-10000` / `city-100000` / `city-500000` / `city-1000000` | 10 тыс. — 1 млн | Исходные 144 объекта плюс городская геометрия за пределами локальной группы ОКС |
| `consumers-17` / `50` / `100` / `500` | 17—500 ОКС | Общие ветви, водный барьер, дорога; сравнение способов группировки |
| `large-simple` | 144 | 3 020 106 043 байта, прежние геометрии и большие неиспользуемые текстовые поля |
| Прежние `examples/stress/*` | см. manifests | Реальные OSM-дороги/вода, сложные пересечения, узкие коридоры, длинные обходы и witness routes |

Городские объекты используют формы полигонов из зафиксированного OSM-слоя
`examples/stress/competition-osm-roads.geojson`, переведённые в EPSG:32637, уменьшенные до размера
квартала и детерминированно размещённые на сетке 80 м. Типы: road, park, water, prohibited_site.
Это **синтетическое размещение реальных форм**, а не реальные дороги по новым координатам.
Происхождение шаблона записано в `template_osm_id`; источник OSM — `examples/stress/osm/provenance.json`.
Вершины не дублируются для увеличения размера. WGS84 сохраняется с 11 десятичными знаками.
Перечисление объектов детерминировано; случайный выбор не используется, seed manifest — 20261016.

Большой текстовый файл специально отделяет размер в байтах от сложности геометрии. Он не служит
доказательством обработки произвольных 3 ГБ координат. Для него отдельная команда:

```bash
python3 scripts/generate-scale-datasets.py --only-large-simple
```

## Что изменено в solver

- Входные метрические XY хранятся компактно, без потери точности и без второй сохраняемой копии
  `Coordinate[]`. Обычный JTS packed sequence оказался хуже из-за soft cache — этот вариант отклонён.
- В больших сценах полный STRtree содержит консервативные envelopes всех препятствий. Буферы,
  PreparedGeometry и границы специальных объектов строятся при обращении. Длинный объект,
  пересекающий область только своей серединой, остаётся кандидатом проверки.
- Начальная навигационная область включает **все** ОКС, существующие линии и камеры плюс 600 м.
  Пространственно выбираются только навигационные контуры. Ограничения и точки присоединения не удаляются.
  Если обычное присоединение и существующий fallback не находят маршрут, область расширяется;
  уже построенные вершины/рёбра сохраняются в пределах попытки. Каждый новый участок проверяется
  полным пространственным индексом и независимым валидатором.
  Проверка длинного водного барьера выявила дефект первого экспериментального варианта: расширение
  требовало 5624 ячейки и ошибочно упиралось в лимит 4096 для уточняющей сетки. Глобальный поиск и
  независимый witness находили допустимый путь. Для расширения применяется основной бюджет графа
  100 000 ячеек; прежний лимит 4096 для дополнительного мелкого уточнения сохранён.
  Второй подтверждённый дефект: длинный обход требовал ДУ900 по длине, но adaptive-кандидат был
  построен по отступам SMALL и отклонялся до существующей процедуры повышения класса. Теперь
  отклонённый кандидат передаёт запрос повторной трассировки с большим классом. Невалидный маршрут
  не принимается; после повторной трассировки он заново проходит полный независимый валидатор.
- Размер одного Feature и оценка накопленной модели ограничены до неограниченной материализации.
  Превышение — `COMPLEXITY_LIMIT`, а не `INVALID_INPUT` и не доказанная недоступность ОКС.

Входная геометрия целиком не отсекается по фиксированному радиусу. Дисковое хранение геометрии
не внедрялось: измеримый выигрыш получен более простым изменением представления и подготовки данных.

## Кластеризация и гидравлика

Экспериментальные кластеры используют расстояния по навигационному графу с препятствиями.
Сравниваются исходный solver, четыре независимых леса и группировка порядка ОКС с общей топологией.
Независимые леса объединяются и проверяются **вместе**; их отдельная валидность не засчитывается
как валидность общей сети. Эти экспериментальные варианты находятся только в test harness.
Кластеризация production solver не включена; точные результаты, включая отрицательные, — в JSON.

Три отдельные гидравлические сети проверяют пути 100+80 м при общей длине 260 м,
постоянный расход на 200 м с technical_node и несколько разветвлений с общим стволом.
Используются и HydraulicCalculator, и независимый ResultValidator, и контрольный инженерный расчёт.
Изменений нормативной гидравлики не потребовалось.

## Подтверждённые измерения

Медианы четырёх прогонов после одного warm-up, одна машина и одинаковые ограничения JVM:

| Проверка | До | После | Результат |
|---|---:|---:|---|
| Конкурсный PLANAR | 26.121 с | 26.386 с | SHA-256 совпадает, 17/17, score 13.4336 |
| Конкурсный DEPTH | 28.011 с | 27.666 с | SHA-256 совпадает, 17/17, score 13.4336 |
| Чтение 1 млн объектов | 11.805 с | 12.538 с | +6.2% времени, геометрия не отбрасывается |
| Heap после чтения 1 млн объектов и GC | 1186.6 МиБ | 631.2 МиБ | −46.8% |
| Пик RSS при чтении 1 млн объектов | 1596.1 МиБ | 963.6 МиБ | −39.6% |

На исходном наборе ускорение не заявляется: различия времени около 1%.
Выигрыш — уменьшение памяти и возможность расчёта сцен, для которых прежняя глобальная
подготовка исчерпывала ресурсы. В прежней сборке подготовка 500 тысяч объектов завершилась
heap OOM при том же `-Xmx2g`; на 10 тысячах глобальный граф достиг лимита навигационных вершин.
Точные результаты полных расчётов, включая размеры графа, heap/RSS и SHA-256, находятся в JSON.

| Городская сцена, PLANAR | Полный расчёт после | Пик RSS после | Подключено / валидация |
|---|---:|---:|---|
| 10 000 объектов | 25.723 с | 769.2 МиБ | 17/17, 0 ошибок/предупреждений |
| 100 000 | 26.785 с | 855.4 МиБ | 17/17, 0 ошибок/предупреждений |
| 500 000 | 32.720 с | 1305.3 МиБ | 17/17, 0 ошибок/предупреждений |
| 1 000 000 | 41.381 с | 1942.5 МиБ | 17/17, 0 ошибок/предупреждений |

Во всех этих сценах выход побайтово совпадает с конкурсным PLANAR-эталоном.
Вместо процента ускорения полного расчёта приводится новый достижимый размер сцены:
полного успешного сопоставимого прогона прежней глобальной реализации на этих размерах нет.
Граф — 5659 вершин, 534010 направленных рёбер, 5565608 проверок видимости;
подготовлено 114 проверочных буферов, все входные препятствия остаются в индексе.
Для тех же размеров медианы DEPTH — 28.014 / 31.320 / 33.579 / 40.565 с;
все пять повторов каждого размера сохранили конкурсный DEPTH SHA-256 и 17/17.

Кластеризация на 100 ОКС: исходный расчёт — 40.065 с, score 23.04243;
группировка с общей топологией — 43.013 с, score 22.09127.
Улучшение score получено ценой времени и памяти; как улучшение масштабируемости этот вариант
не принят. Независимые группы на 17/50/100 ОКС не прошли валидацию объединённой сети.
На исходном конкурсном наборе независимые группы были валидны, но ухудшили score до 15.15670.
Плотная сцена с 500 ОКС остановилась по существующему лимиту 50 млн проверок видимости;
результаты кластерных вариантов для неё не заявляются.

Отдельная сцена с 1.5 млн объектов остановлена контролируемо при чтении Feature #1171012
(нумерация с нуля): оценка модели достигла бюджета 55% heap. Пик RSS — около 1059 МиБ;
причина — `COMPLEXITY_LIMIT`, без OOM. Это не утверждение о геометрической недоступности ОКС.

Файл `large-simple` размером 2.81 ГиБ прошёл по пять PLANAR/DEPTH-расчётов с эталонными SHA-256:
медианы полного расчёта — 29.477 / 33.631 с. Чтение отдельно стало медленнее: 2.259 → 6.367 с;
это зафиксированный компромисс данной реализации контроля ресурсов, а не ускорение.
Пик RSS при чтении — 796.3 → 823.4 МиБ, heap после GC — около 10 МиБ.
Скорость изолированного чтения нельзя складывать со временем solver из другой серии замеров.

## Проверка инженерной корректности

Полный Java suite: 412 тестов, без failures/errors/skipped; UI: 6 тестов.
Добавлены 26 regression-тестов: компактные координаты, отложенная подготовка ограничений,
локальный граф и расширение, длинный обход с повышением класса, гидравлические пути,
контроль ресурсов parser. Нормативные формулы не изменялись.

68 повторных прогонов: 15 универсальных сцен и 2 плотные/смешанные сцены в PLANAR/DEPTH,
без ошибок/предупреждений.
Все их выходы побайтово совпали с предыдущей проверенной версией.
Реальные OSM-дороги и OSM-дороги с водой: 17/17; best score PLANAR 14.142099592,
DEPTH 14.138740444. Эти scores относятся к изменённому входу, а конкурсный score остаётся 13.4336.
Невозможная водная сцена корректно оставляет ОКС неподключённым; solver честно сообщает об
исчерпании поиска без собственного доказательства недоступности. Ожидание 0 подключений
обосновано отдельно геометрией fixture, а не одним результатом поиска.

Docker build/run проверен на неизменённом Dockerfile. SHA-256 production-классов внутри JAR
совпадает с замороженной сборкой, на которой выполнялись тесты и замеры. Изолированный smoke
проверил health=UP, конкурсный PLANAR, DEPTH узкого коридора, независимый API-валидатор,
контролируемый FAILED при превышении бюджета Feature, следующий успешный job, рестарт и
сохранность записей. Production-контейнеры, runtime и volumes не изменялись.

Всего финальная сборка прошла 60 полных benchmark-расчётов (конкурсный набор, четыре городских
размера и большой простой файл, оба режима, warm-up + 4 повтора) и 68 отдельных stress-прогонов.
У серии DEPTH на 100 тысячах объектов управляющая сессия была прервана: все пять JVM-замеров
и выходов успели сохраниться и проверены, но код завершения родительского процесса неизвестен.
Это явно отражено в metadata; время всего процесса для этой серии не выдумывается.

## Методика и границы выводов

Замеры выполнены последовательно на одном локальном Docker engine: Java 11, 8 CPU quota,
container memory 4 ГиБ, JVM heap 2 ГиБ. Один warm-up исключается, затем берётся медиана четырёх
прогонов в той же JVM. Heap/RSS измеряются каждые 10 мс; retained heap — после GC.
Retained heap включает весь занятый heap JVM после чтения, в том числе объекты parser/runtime;
это не изолированный подсчёт размера одних геометрий.
Полный расчёт здесь — CLI: чтение, solver, запись результата и независимая проверка;
HTTP-загрузка, ожидание очереди и старт Spring в это время не входят.
Это измеренные значения, а не строгая верхняя оценка всех будущих аллокаций.
В отчёте отдельно отмечены холодные прогоны, OOM и истечение бюджета времени эксперимента.
Жёсткого нормативного времени расчёта не вводится.

Остаются ограничения:

- вся входная модель и полный индекс находятся в heap; out-of-core обработки нет;
- распределённая по всему городу существующая сеть увеличивает начальную область графа;
- поиск ограничен явными бюджетами узлов, рёбер, проверок видимости и расширения сетки;
- оценка модели и лимит Feature снижают риск OOM, но не доказывают безопасность любой операции JTS;
- миллион объектов в этих сценах — преимущественно удалённые ограничения при прежних 17 ОКС;
  это не миллион потребителей и не доказательство разрешимости произвольного городского набора;
- математическая полнота и произвольная сложность входа до 3 ГБ не заявляются.

Старые 77 с на сервере и прежняя доля CPU в JTS не используются как доказательство ускорения.
Серверные настройки, API, frontend, нормативы стоимости и гидравлики не менялись. Git operations: 0.
