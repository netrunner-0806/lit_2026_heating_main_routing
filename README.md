# heatnet-router

Сервис автоматизированного проектирования трасс подключения объектов капитального строительства
к существующим тепловым сетям. Вход — GeoJSON с сетью, камерами, точками потребления и ограничениями.
Результат — до трёх проверенных вариантов новой сети с геометрией, диаметрами, стоимостью и ранжированием.

## Возможности

- Совместное подключение потребителей через общие магистрали и ответвления.
- Поиск маршрутов с учётом зданий, водоёмов, железных дорог и специальных пересечений коммуникаций.
- Присоединение через существующие или новые камеры с проверкой числа примыканий.
- Расчёт расходов, выбор ДУ и проверка непрерывных длин по нормативным таблицам задачи.
- Расчёт стоимости участков, камер, врезок и штрафов за неподключённые точки.
- Режим PLANAR для расчёта в плане и DEPTH для совместного выбора трассы и вертикального профиля.
- Проверка выходной геометрии, топологии, гидравлики, стоимости и рангов.
- Асинхронные задания, возобновляемая загрузка больших файлов, сохранение входа и результата.

## Архитектура

Backend написан на Java 11 и Spring Boot 2.6.3. HTTP-контроллеры принимают данные и выдают результаты;
расчёт выполняется в ограниченной очереди рабочих потоков. PostgreSQL хранит состояния заданий,
диагностику и сводки, файловое хранилище — входные и выходные GeoJSON и журналы загрузок.

JTS выполняет геометрические операции и пространственные запросы. Proj4J преобразует WGS84 в
метрическую систему координат. Навигационный граф и Dijkstra реализованы собственными классами
`NavGraph` и `PathSearch`; зависимости JGraphT в текущей сборке нет.

Frontend — статические HTML/CSS/JavaScript с Leaflet, раздаваемые Spring Boot. Библиотека Leaflet
включена в JAR через WebJar; картографическая подложка запрашивается по сети. Docker Compose запускает
приложение, PostgreSQL и Caddy. Caddy обслуживает HTTPS и передаёт запросы backend.

```text
Браузер / HTTP-клиент → Caddy → Spring Boot → очередь → solver → проверка результата
                                  │                       │
                                  ├── PostgreSQL          └── GeoJSON
                                  └── файловое хранилище
```

## Алгоритм

GeoJSON читается потоком, координаты переводятся в метры, для ограничений и существующей сети строятся
пространственные индексы. Solver формирует навигационные вершины и точки возможных врезок, затем
последовательно строит сеть по пяти стратегиям с разным порядком подключения и предпочтениями.

**Кандидат подключения оценивается по результату изменения всей проектируемой сети.** Новая ветвь
может использовать уже проектируемый ствол вместо независимой линии, но увеличивает его расход
и может потребовать большего ДУ. Поэтому в пробной копии пересчитываются гидравлика, диаметры,
предельные длины, камеры и DEPTH-профили. Сравниваются полная стоимость и длина полученной сети,
а не только цена добавляемой ветви.

После локального улучшения завершённые варианты проходят валидацию, сортируются по score и очищаются
от близких дубликатов. Неудача отдельной стратегии не уничтожает другие завершённые варианты.
Это эвристический поиск инженерно допустимой сети. Постановка, правила, вычислительные бюджеты и
диагностика описаны в [документе об алгоритме](docs/algorithm.md).

## Запуск

Нужны Docker Engine с Compose и свободные порты 80/443. Локальная Java для запуска в контейнерах
не требуется. Команды выполняются из корня проекта:

```bash
cp .env.example .env
# Укажите собственный POSTGRES_PASSWORD и проверьте JAVA_OPTS под память машины.
docker compose -p heatnet config --quiet
docker compose -p heatnet up -d --build
docker compose -p heatnet ps
curl -k https://localhost/actuator/health
```

При `DOMAIN=localhost` UI доступен по **https://localhost/**; локальный сертификат Caddy потребует
доверия в браузере. `curl -k` здесь используется только для локальной проверки. Swagger UI:
**https://localhost/swagger-ui.html**. Для публичного домена используется обычная проверка TLS.

Шаблон окружения рассчитан на машину с 16 ГБ RAM и задаёт `-Xmx13g`. Это предел heap, а не предел
памяти контейнера. На машине с меньшим объёмом RAM уменьшите его до запуска. Подробности о PostgreSQL,
volumes, запуске опубликованного образа и обновлении — в [инструкции развёртывания](docs/deployment.md).
Синтаксис обоих Compose-файлов проверен командой `config --quiet` на Compose v5.2.0.
Статус проверки старой версии 1.29.2 описан в инструкции развёртывания.

## Использование

1. Откройте UI и выберите GeoJSON `FeatureCollection`.
2. Выберите PLANAR или DEPTH и запустите расчёт.
3. Для большого файла интерфейс покажет передачу по частям. После обрыва или обновления страницы
   выберите тот же файл повторно: подтверждённые части не отправляются заново.
4. Дождитесь завершения задания. Передача файла и расчёт имеют отдельные состояния.
5. Сравните варианты на карте и по сводкам. Проверьте подключённые точки, диагностику и отчёт валидации.
6. Скачайте GeoJSON или инженерный отчёт. Для сравнения режимов повторите расчёт сохранённого входа.

При расчёте показаны фактический этап, режим выполнения, завершённые стратегии и работающие
стратегии. Процент вычислений не оценивается: состояние «завершено» появляется после сохранения
проверенного результата.

Галочки «Вариант 1», «Вариант 2», «Вариант 3» в легенде карты управляют видимостью сетей.
По умолчанию показан V1; выбор нескольких вариантов автоматически включает сравнение.
V1 — синий, V2 — оранжевый, V3 — фиолетовый, с постоянными разными штрихами.
Совпадающие линейные участки в плане (допуск 5 см) приглушаются автоматически, включая обратное
направление и разбиение линий. Это визуальное сравнение, а не проверка совпадения ДУ или
DEPTH-профилей. Для слишком сложной геометрии остаётся обычное наложение. Компактная таблица
показателей видна только в режиме сравнения; значения берутся из результата solver.

Для небольшого входа можно использовать HTTP:

```bash
curl -k -F 'file=@input.geojson' -F 'mode=PLANAR' -F 'maxVariants=3' \
  https://localhost/api/v1/jobs
```

Ответ `202` содержит ID задания. Пошаговые примеры, протокол загрузки и HTTP-ошибки — в [API](docs/api.md).

## Входные и выходные данные

Координаты входа и выхода — `[долгота, широта]`, WGS84. Поддерживаются существующие тепловые линии
`heat_network`, камеры `heat_chamber`, источники `source`, потребители `oks_connection_point` и
ограничения `restriction`. Потребителю нужны ID и положительный `flow_tph`; существующей линии — ДУ.
Здание задаётся ограничением типа `oks`, а не отдельным типом потребителя.

Выход содержит только новые линии, новые камеры, технические узлы и `variant_summary`.
Варианты объединены в один `FeatureCollection` и различаются по `variant_id`. Существующие объекты
остаются во входном файле; результат ссылается на их ID. Длины заданы в метрах, расходы — в т/ч,
стоимости — в рублях. Описание свойств и единиц приведено в [API](docs/api.md).

## Тестирование

Для локальной сборки нужны JDK 11 и Maven; для JavaScript-тестов — Node.js с `node:test`
(в CI используется Node.js 24).

```bash
mvn -B -DskipTests package
mvn test
node --test src/test/js/*.test.cjs
```

`-DskipTests` компилирует тесты, но не выполняет их. Java-тесты используют H2 в тестовом профиле,
а не production PostgreSQL. Fixtures находятся в `src/test/resources`: небольшие сцены, геометрические
witness-маршруты и эталоны результата. Конкурсный regression-вход можно переопределить через
`-Dheatnet.corrected.input=/path/to/input.geojson`.

В `src/test/java/ru/lct/heatnet/oracle` находятся независимые тестовые проверки расстояний, стоимости,
гидравлики и повреждённых результатов. Runtime-валидатор восстанавливает сеть из результата,
но часть нормативных и расчётных функций разделяет с solver; различие описано в документации алгоритма.
Полная Java-регрессия включает расчёты геометрических сцен и может занимать заметное время.
