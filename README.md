# Сервис моделирования трасс подключения к тепловым сетям

Сервис принимает GeoJSON с существующей тепловой сетью, камерами, точками подключения объектов капитального
строительства (ОКС) и пространственными ограничениями. Автоматически строит новую сеть с возможностью общих
участков, рассчитывает расходы, условные диаметры (ДУ) и стоимость. Результат — до трёх вариантов в GeoJSON,
их ранжирование и отчёт независимого валидатора; варианты можно просмотреть на карте.

## Возможности

- Обязательный двумерный режим `PLANAR`: маршруты, камеры и специальные проходы с учётом ограничений.
- До трёх различающихся вариантов подключения в каждом расчёте.
- Совместное подключение нескольких ОКС с общими участками и разветвлениями в камерах.
- Расчёт суммарных расходов, минимальных ДУ и предельной длины непрерывного пути одного ДУ.
- Стоимость строительства, штраф за неподключённые точки и итоговый показатель `score`.
- Независимая проверка результата по входным данным: геометрия, топология, расходы, ДУ и стоимость.
- Дополнительный режим `DEPTH`: отдельная трассировка с вертикальным профилем и учётом глубины в стоимости.

### Фактическая конфигурация решения

В проекте используются Java 11, Spring Boot и родительский POM 2.6.3, `springdoc-openapi-ui` 1.7.0.
Docker-сборка выполняется Maven 3.9.6; база — PostgreSQL 16 (`postgres:16-alpine`). Приложение
работает на порту 8080 внутри контейнера. Для сервера 8 CPU / 16 ГБ RAM в Docker Compose заданы
`HEATNET_WORKERS=1` (один расчёт одновременно) и
`JAVA_OPTS=-Xms1g -Xmx13g -XX:+UseG1GC -XX:+ExitOnOutOfMemoryError`.
Начальный Java heap — 1 ГиБ, максимальный — 13 ГиБ. Переменные окружения и `.env` могут переопределять
эти значения; при обновлении существующего развёртывания нужно также обновить ранее заданные значения.

При heap OOM JVM завершается целиком, после чего `restart: unless-stopped` поднимает приложение снова.
При старте незавершённые задания `QUEUED`/`RUNNING` переходят в `FAILED`; полностью сохранённый input
остаётся доступен для повторного расчёта. Healthcheck проверяет HTTP success и `status=UP` на
`/actuator/health` каждые 30 с (timeout 5 с, retries 3, start period 60 с).
Статус `unhealthy` служит для диагностики и сам по себе не вызывает перезапуск Compose.

Загрузка сохраняется на диск; multipart использует дисковый спул после 1 МБ, лимит файла — `3GB`, всего запроса — `4GB`
с учётом служебных данных multipart. В Docker Compose спул находится на томе данных: при поддержке
перемещения сервлет-контейнером файл переносится в каталог задания без повторного полного копирования. GeoJSON разбирается по одному объекту, результат записывается потоково и скачивается с диска.
PostgreSQL хранит задания, сводки и отчёты; входные и выходные GeoJSON хранятся в файловом томе.
Показатели 50 пользователей и файлы 3 ГБ / 500 МБ — целевые требования, а не подтверждённые здесь результаты
нагрузочных испытаний. Ограничения памяти расчётной модели и карты описаны ниже.

## Формат входа

Один GeoJSON `FeatureCollection` в EPSG:4326 / WGS84; координаты записываются как `[долгота, широта]`.
Атрибуты каждого объекта находятся в `properties`. Обязательный состав:

| `object_type` | `geometry.type` | Обязательные свойства |
|---|---|---|
| `source` | `Point` | `id`, `object_type` |
| `heat_network` | `LineString` | `id`, `object_type`, `diameter` (ДУ, мм) |
| `heat_chamber` | `Point` | `id`, `object_type` |
| `oks_connection_point` | `Point` | `id`, `object_type`, `flow_tph` (положительный расход, т/ч) |
| `restriction` | `LineString`, `MultiLineString`, `Polygon`, `MultiPolygon` | `id`, `object_type`, `restriction_type` |

Типы ограничений: `oks`, `water`, `railway`, `park`, `social_area`, `prohibited_site`, `road`,
`tram_tracks`, `gas_pipeline`, `power_cable`. Здания задаются как `restriction` с типом `oks`;
принадлежность точки зданию определяется пространственно. Каждая точка подключения, включая несколько
точек в одном здании, — самостоятельный потребитель. `id` может быть строкой или числом;
исходный тип сохраняется в ссылках на входные объекты и в списке неподключённых точек.

Реализация дополнительно принимает `MultiLineString` существующей сети. Неизвестные `restriction_type`
по умолчанию игнорируются с предупреждением (`unknownRestrictionPolicy=IGNORE`); политика `FORBIDDEN`
считает их запретом с отступом 1 м. Диагностику входа следует проверить перед использованием результата:
парсер может пропускать некорректные объекты с предупреждениями. Отсутствие пригодной существующей сети,
точек подключения или положительного числового `flow_tph` у точки приводит к ошибке расчёта.
Пример входа: [examples/depth-demo.geojson](examples/depth-demo.geojson).

## Формат результата

Для каждого режима возвращается отдельный GeoJSON `FeatureCollection` в WGS84. Внутри файла варианты
различаются `variant_id`; каждый объект содержит `id`, `object_type`, `variant_id`.

| `object_type` | Геометрия | Содержание |
|---|---|---|
| `heat_network` | `LineString` | Новый участок: `start_node_id`, `end_node_id`, `flow_tph`, `diameter`, `length`, `laying_method`, `depth_start`, `depth_end`, `cost` |
| `heat_chamber` | `Point` | Новая камера: `diameter` — наибольший ДУ примыкающих участков, `cost` — стоимость камеры |
| `technical_node` | `Point` | Смена параметров участка без разветвления; отдельной стоимости нет |
| `variant_summary` | `null` | Одна сводка на вариант: стоимости, длина, штраф, `score`, `rank`, `unconnected_oks_ids` |

Один линейный объект представляет пару труб одного ДУ; расход пары не удваивается. `length` задаётся
в метрах по горизонтальной проекции, `cost` — в рублях, `laying_method` — `base` или `special`.
В `PLANAR` глубины равны `null`; в `DEPTH` они задаются в метрах. Дополнительные атрибуты `k_spec`,
`k_depth`, `slope` и `crossings` поясняют коэффициенты, уклон и вертикальные пересечения.

Ссылки `start_node_id` / `end_node_id` указывают на точку подключения ОКС, существующую или новую камеру
либо технический узел; координаты узлов совпадают с концами линии. Существующие объекты берутся из входа
и повторно в выход не включаются. Направление записи координат не задаёт направление потока.

В сводке `construction_cost` включает стоимость новых участков, новых камер (`chamber_construction_cost`)
и врезок в существующие камеры (`existing_chamber_tie_in_count`, `existing_chamber_tie_in_cost`).
`calculated_cost` равна `construction_cost + unconnected_penalty`; `new_network_length` — суммарная длина
новых участков. `rank=1` соответствует наименьшему `score`. `unconnected_oks_ids` содержит исходные ID
неподключённых `oks_connection_point`; при полном подключении массив пуст.

## Алгоритм

1. **Разбор и CRS.** Вход сохраняется на диск и читается потоково по объектам с диагностикой геометрии
   и атрибутов. Для расчёта длин, расстояний и габаритов координаты переводятся в EPSG:32637 (UTM 37N).
2. **Ограничения.** Формируются запрещённые зоны с отступами и габаритами пары труб, а также правила
   специальных проходов. Для собственного ОКС предусматривается финальный прямой участок;
   исключение из отступа относится только к собственному полигону, остальные ограничения действуют.
   Пересечение `railway` запрещено. От камеры на существующей сети внутри `road` / `tram_tracks`
   спецпроход идёт прямо до выхода и ещё 3 м за границу; со стороны камеры дополнительные 3 м не нужны.
   Для газопровода, кабеля и пересечения существующей теплосети спецучасток — ±2 м вдоль оси новой сети,
   без добавления половины габарита.
3. **Кандидаты и граф.** Выбираются выходы из ОКС, существующие камеры, точки на существующей сети
   и возможные развилки на новой сети. Строится граф видимости вокруг препятствий; алгоритм Дейкстры
   находит маршруты, которые затем спрямляются с проверкой допустимости и поворотов до 90°.
4. **Совместное подключение.** Точки последовательно присоединяются к существующей сети или уже построенной
   ветви, образуя дерево либо лес без циклов. Кандидаты оцениваются по стоимости всей получающейся сети;
   общие участки обслуживают несколько потребителей, развилки размещаются в камерах с максимум четырьмя
   примыканиями. В пределах 10 м используется пригодная существующая камера; иначе создаётся новая
   камера на существующей линии. Локальное переприсоединение улучшает найденный вариант.
5. **Расходы и ДУ.** На общих участках суммируются расходы потребителей. Выбирается минимальный ДУ,
   удовлетворяющий расходу, предельной длине и неубыванию ДУ к существующей сети. Длина одного ДУ
   накапливается по каждому пути через камеры и технические узлы; параллельные ветви не суммируются.
   При неизменном расходе ДУ одинаков по всей части сети: если длина требует увеличения, повышается ДУ
   всей этой части, независимо от геометрических разбиений и спецучастков.
   При увеличении требуемого класса отступа выполняется повторная трассировка.
6. **Стоимость и варианты.** Разные порядки подключения и политики выбора места присоединения дают
   варианты. Стоимость участка равна `L × c(ДУ) × Kспец × Kdepth`; в обычном 2D-участке оба коэффициента
   равны 1. При наложении спецпроходов берётся максимальный `Kспец`. Добавляются камеры, врезки
   в существующие камеры по 5 000 000 руб. за новый примыкающий участок и штрафы. Стоимость новой камеры
   уже включает присоединение. В `DEPTH` профиль и его стоимость участвуют в оценке каждого кандидата.
7. **Независимая валидация и ранжирование.** По входу и сформированным выходным объектам проверяются
   топология, геометрия, расходы, ДУ, стоимость и правила выбранного режима. Кандидаты с ошибками
   и дубликаты отбрасываются. До трёх оставшихся вариантов получают ранг по возрастанию
   `score = 0.7 × (calculated_cost / 25 000 000) + 0.3 × (new_network_length / 100)`.
   `S` ранжирует варианты одного решения и не является единственным критерием оценки конкурсного решения.
   Ровно три варианта не требуются; ограничения стоимости «не более +15% к лучшему» нет.

## Если маршрут для ОКС не найден

Сервис продолжает рассчитывать остальные точки и сохраняет частичный результат прошедшего проверку варианта.
Исходные ID неподключённых точек попадают в `variant_summary.unconnected_oks_ids`, причины отказа доступны
в журнале решений. За каждую такую точку начисляется штраф `100 000 000 + 500 000 × flow_tph` руб.,
включаемый в `unconnected_penalty`, итоговую стоимость и `score`.

Найденное допустимое подключение не отклоняется ради более выгодного штрафа: перед отказом расширяется
поиск кандидатов и снимаются предпочтения стратегии, например «только существующие камеры», при сохранении
геометрических правил. Локальное улучшение также сохраняет уже подключённого потребителя.
Результат «маршрут не найден» относится к выполненному эвристическому поиску и не доказывает математическую
недостижимость. Если ни один вариант не прошёл проверку, задание получает статус `FAILED`;
это отличается от успешно рассчитанного частичного варианта со статусом `DONE`.

При старте приложения прерванные `QUEUED` / `RUNNING` переводятся в `FAILED` с причиной перезапуска.
Неполные файлы удаляются; полностью сохранённый вход остаётся доступным для повторного расчёта через API.
Автоматическое восстановление рассчитано на один экземпляр приложения, как в Docker Compose.

## Режим с учётом глубины

`DEPTH` выполняет отдельную трассировку: плановый маршрут, профиль и стоимость рассматриваются совместно
при оценке кандидатов присоединения. Если вертикальные требования невыполнимы, кандидат отклоняется
и ищутся альтернативные маршруты в плане. Варианты `DEPTH` ранжируются отдельно от `PLANAR`.

Глубина `h` измеряется от условной горизонтальной поверхности до **верха габарита** новой сети.
Обычная глубина — 3.0 м, минимум — 0.7 м, максимальный модуль уклона — 0.10 м/м по горизонтальной длине.
Актуальное ТЗ не задаёт дискретный шаг или максимальную глубину; численный предел реализации указан
в границах применения. Z-координаты не требуются: профиль передаётся через `depth_start` и `depth_end`.

| Пересекаемый объект | Вертикальное условие |
|---|---|
| Дорога | Проход под объектом; верх новой сети не мельче 1.0 м |
| Трамвайные пути | Проход под объектом; верх новой сети не мельче 1.2 м |
| Газопровод | `ABOVE` / `BELOW`, просвет между габаритами не менее 0.2 м; верх газопровода 2.8 м, высота 0.40 м |
| Силовой кабель | `ABOVE` / `BELOW`, просвет не менее 0.5 м; верх кабеля 2.7 м, высота 0.20 м |
| Существующая тепловая сеть без присоединения | `ABOVE` / `BELOW`, просвет не менее 0.5 м; верх 3.0 м, высота по её ДУ |

На спецучастках формируются плато постоянной глубины. Для вариантов `ABOVE` / `BELOW` пересекаются
допустимые интервалы глубин всех наложенных ограничений, проверяются уклоны и глубины в узлах.
Между плато строятся подъёмы, спуски и возврат к 3.0 м; между близкими препятствиями изменённая глубина
может сохраняться. Общий участок имеет единый профиль, ветви принимают его глубину в камере.
После изменения расходов и ДУ профили рассчитываются заново.

Коэффициент `Kdepth` (`Kгл`, в выходе `k_depth`) равен 1 при `h <= 3.0`, иначе
`1 + 0.10 × (h − 3.0)`. На равномерном подъёме или спуске используется среднее коэффициентов на концах.
При пересечении глубины 3.0 м создаётся технический узел и участок делится. Длины для стоимости,
предельной длины и `score` остаются горизонтальными. Независимый валидатор проверяет глубины, просветы,
уклон, непрерывность профиля и стоимость.

## Границы применения

- Решение работает с расчётной моделью, справочниками и типами объектов актуального приложения ЛЦТ,
  в метрической системе EPSG:32637. Реальный рельеф, геология и фактические отметки коммуникаций
  не моделируются. Полный расчёт давления, потерь напора и мощности источника, рабочее проектирование
  и реконструкция существующих сетей и камер в эту модель не входят. Текущий расход и резерв
  пропускной способности существующей сети не определяются.
- Поиск эвристический: глобальный минимум стоимости и нахождение каждого существующего допустимого
  маршрута не гарантируются. Конечный граф, консервативные отступы по классам ДУ и бюджеты кандидатов
  могут исключить узкий коридор или сложное подключение. Расширенный поиск ограничен 1000 оценками
  кандидатов и 15 с на подход; в `DEPTH` рассматривается до 8 альтернативных маршрутов на кандидата. Размер вспомогательной сетки предварительно оценивается по охвату объектов;
  предел — 100 000 ячеек, предел графа — 100 000 навигационных узлов. Превышение приводит
  к контролируемому отказу расчёта.
  Организаторы не устанавливают жёсткий лимит времени расчёта; проверочный набор может иметь масштаб Москвы.
- Для собственного ОКС сначала проверяется ближайшая точка границы; если через неё подключение не найдено,
  перебираются другие точки границы. Точка вне полигона может быть отнесена к ближайшему ОКС в пределах
  его отступа. Выбор другой допустимой границы разрешён разъяснениями от 29.09.2026; отнесение внешней
  точки к ближайшему ОКС остаётся интерпретацией реализации.
- Около спецпересечений исключение из горизонтального отступа проверяется в расширенной окрестности:
  её радиус определяется протяжённостью спецучастка и удвоенным расстоянием с учётом габаритов класса ДУ.
  Эта геометрическая интерпретация реализации шире буквальной границы спецучастка в ТЗ; прохождение
  встроенной проверки само по себе не снимает вопрос соответствия этого допущения.
- В `DEPTH` глубина у существующей сети фиксирована на 3.0 м; у ОКС выбирается ближайшая достижимая
  к 3.0 м глубина. Возврат между плато выполняется, если помещаются уклоны и минимум 5 м обычной глубины.
  Профиль магистрали не переоптимизируется ради боковой ветви с невыполнимым профилем — такой кандидат
  отклоняется. Численный предел расчёта и валидатора — 100 м; это ограничение реализации, а не требование ТЗ.
- Для неизвестных типов ограничений действует выбранная политика `IGNORE` / `FORBIDDEN`;
  сервис не определяет их инженерный смысл автоматически. Предупреждения парсера могут означать
  пропуск объекта, исправление геометрии или замену отсутствующего диаметра максимальным габаритом.
- Потоковый ввод-вывод не устраняет расход памяти на отдельный GeoJSON-объект, всю расчётную геометрию,
  граф и список выходных объектов. UI получает исходные слои только через ограниченный предпросмотр
  для входов до 10 МиБ; большие входы для карты не скачиваются. Результат загружается целиком, поэтому
  объём выходной геометрии также влияет на память браузера. Передача через API не гарантирует
  расчёт произвольной сцены в пределах heap.
  Требуются свободное дисковое место для входов, результатов и временного спула и оценка сложности данных.

Расчётные правила и формат данных определяются «Техническим приложением ЛЦТ.docx» с учётом
«Разъяснений по вопросам ЛЦТ.docx» и новых «Дополнительных разъяснений по вопросам участников 29.09.2026.docx».

## API

Полная документация REST API доступна в Swagger UI: <http://localhost:8080/swagger-ui.html>.
Спецификация OpenAPI: <http://localhost:8080/v3/api-docs>.

Пример загрузки файла и запуска расчёта:

```bash
curl -F 'file=@input.geojson' 'http://localhost:8080/api/v1/jobs?mode=PLANAR'
```

Ответ `202` содержит `id` задания. Статус доступен по `GET /api/v1/jobs/{id}`; после `DONE` результат
скачивается по `GET /api/v1/jobs/{id}/result.geojson`. Для дополнительного режима задайте `mode=DEPTH`.
Сводки и отчёт валидатора доступны по `GET /api/v1/jobs/{id}/result`, журнал решений — по
`GET /api/v1/jobs/{id}/explain`. Независимая проверка входа и результата описана в Swagger
для `POST /api/v1/validate`.
