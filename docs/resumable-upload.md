# Возобновляемая загрузка GeoJSON

Веб-интерфейс передаёт файл частями через `/api/v1/uploads`. Старый multipart endpoint
`POST /api/v1/jobs` сохранён. Максимальный размер файла берётся из действующего
`spring.servlet.multipart.max-file-size=3GB` (3 × 1024³ байт). Успешная передача файла
не означает успешного расчёта: статусы задания и его диагностика показываются отдельно.

## Протокол

Все запросы сессии содержат `X-Upload-Token`: случайный секрет владельца, 64 шестнадцатеричных
символа. Токен создаёт клиент через криптографический генератор; сервер хранит только SHA-256.
Секрет не передаётся в URL. Общей пользовательской авторизации в приложении нет;
эта защита распространяется на upload sessions, а существующие job endpoints сохраняют свою модель доступа.
Для рабочего сайта требуется HTTPS; локальные испытания используют localhost.

| Запрос | Назначение |
|---|---|
| `POST /api/v1/uploads` | Создать сессию или получить уже созданную с теми же ID, секретом и параметрами |
| `GET /api/v1/uploads/{id}` | Состояние, подтверждённые индексы/хеши частей, число принятых байт |
| `PUT /api/v1/uploads/{id}/parts/{index}` | Бинарная часть, `Content-Type: application/octet-stream`, `X-Part-SHA256` |
| `POST /api/v1/uploads/{id}/complete` | Проверить целостность, передать полный файл заданию; вернуть тот же `jobId` при повторе |
| `DELETE /api/v1/uploads/{id}` | Отменить незавершённую передачу |

Создание принимает `uploadId` (UUID клиента), `filename`, `totalSize`, `chunkSize`, `fingerprint`,
`mode`, `maxVariants`, `unknownRestrictionPolicy`. Тело метаданных ограничено 8 КиБ.
По умолчанию часть — 16 МиБ; протокол допускает 8–32 МиБ. Последняя часть содержит остаток файла.
Интерфейс отправляет не более двух частей одновременно. Запрос не может записать данные за пределами
своего диапазона. Повтор одинаковой части проверяется без изменения ранее сохранённых байт;
конфликтующий SHA-256 возвращает 409, неверная сумма фактически полученных байт — 422.

Клиент использует `File.slice()`, вычисляет SHA-256 ограниченного буфера одной части и сохраняет
ID/секрет/параметры в localStorage. При сетевой ошибке или HTTP 429/500/502/503/504 выполняются
до пяти попыток с увеличивающейся задержкой; затем загрузка приостанавливается. Для продолжения
после перезагрузки страницы нужно повторно выбрать файл. Проверяются имя, размер, время изменения,
хеш образцов начала/середины/конца и полные хеши уже подтверждённых частей. Повторно передаются только
неподтверждённые части. Файл целиком не читается в ArrayBuffer и не разбирается как JSON в браузере.

## Хранение и восстановление

Сессии находятся в `<heatnet.storage-dir>/.uploads/<UUID>`. Имя пользовательского файла
не участвует в формировании пути. Данные записываются по смещениям в один файл с буфером 64 КиБ.
Подтверждение сохраняется только после `force()` данных и атомарной замены JSON-журнала сессии.
Операции одной сессии сериализованы; незавершённый диапазон после обрыва можно перезаписать.

Состояния: `UPLOADING → READY → COMPLETED`, а также `CANCELLED` / `EXPIRED`.
`complete` заново потоково проверяет суммы всех частей и вычисляет SHA-256 файла перед переходом в READY.
Полный файл публикуется для заранее закреплённого `jobId` жёсткой ссылкой на том же filesystem,
без второй полной копии. Это требует поддержки hard links, атомарного rename и fsync каталогов;
штатный Linux storage volume подходит. При ошибке хранилища операция завершается контролируемо.

Сбой БД или очереди не удаляет READY-файл. Отказ очереди переводит запись задания в FAILED
с признаком возможности повторить complete. Повтор использует тот же ID. Атомарный переход
QUEUED → RUNNING допускает только одного исполнителя даже при повторной доставке в очередь.
После аварийного рестарта прежние QUEUED/RUNNING становятся FAILED по существующей recovery-логике;
они автоматически не запускаются повторно. Полностью принятый input сохраняется, включая ошибки
расчёта и COMPLEXITY_LIMIT. Незаконченные upload sessions при этом остаются возобновляемыми.

Неактивная передача истекает через 24 часа. Ежечасная очистка пропускает сессии с выполняющейся
операцией и удаляет только их временные данные; input зарегистрированного задания не удаляется.
Небольшие журналы завершённых/отменённых сессий сохраняются для идемпотентности и диагностики.
Реализация рассчитана на существующее развёртывание с одним экземпляром app, а не на несколько
процессов, совместно записывающих в один storage volume.

## Проверки

Генерация валидных GeoJSON на 100 МиБ, 1 ГиБ и 2,8 ГиБ с исходной конкурсной геометрией
и воспроизводимым текстовым заполнением (это проверка передачи, не сложности маршрутизации):

```bash
python3 scripts/generate-upload-fixtures.py
```

Серверные и клиентские regression-тесты:

```bash
mvn test
node --test src/test/js/*.test.cjs
```

Реальные испытания используют отдельный Compose project и исходный Caddyfile, не production volumes.
Команды и результаты приёмки сохраняются в машинном verification report.
